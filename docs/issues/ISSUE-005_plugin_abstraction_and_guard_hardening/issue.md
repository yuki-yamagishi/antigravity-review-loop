# Issue #5: プラグインの抽象化・設定層導入とDoR/安全ガードの是正

## 1. 解決すべき課題・背景 (Why)

- **現在の問題点**: 
  `antigravity-review-loop` を特定プロジェクト（JobEval）から汎用プラグインとして切り出したものの、特定プロジェクト名（JobEval）の残存のみならず、設計上の負債が残存している。具体的には以下の4点が問題である：
  1. `safetyGuard.js` が `npm test`（非対話設定）を対話型と誤認して拒絶し、さらに npm の引数解釈（`--` の有無）を考慮していないため誤判定・誤拒絶が生じる。
  2. プラグイン標準テンプレート（`template_issue.md`）の未記入プレースホルダー（`<ISSUE_NUMBER>` や空欄項目）を `branchDoRGate.js` が検知できず、未記入テンプレートがすり抜ける。
  3. ホストプロジェクトごとの差異（テストスクリプト名、Issue ディレクトリ、見出し、ラベル名等）を吸収する設定層が存在せず、特定の規約にハードコードされている。
  4. プラグインルートおよびテンプレートへのパスが `.agents/plugins/...` に固定され、環境や配置場所に応じた動的解決がなされていない。
- **背景と真の動機**: 
  本プラグインをあらゆる Antigravity 開発環境において安全かつ摩擦なく導入可能にし、AI エージェントが自律的かつ堅牢に品質ガバナンスとレビュー自己修復を遂行できるようにする。
- **放置した場合の影響**: 
  他リポジトリ導入時に正規のテスト実行が不当に遮断され、未記入の仕様書でブランチ作成がすり抜け、パス不整合によるエラーやスクリプト実行失敗が多発する。

---

## 2. 変更内容の概要 (What)

1. **設定層（Config Layer）の導入**:
   - プラグイン共通設定ローダー（`config/reviewLoopConfig.js`）を新設。
   - ホスト側の `.agents/review-loop.config.json`（存在する場合）を読み込み、存在しない場合は安全な汎用デフォルト値にフォールバック。
   - テストコマンド許可リスト、docs パス、ラベル、見出しキーワード、ADR 同期有無などを柔軟に設定可能とする。
2. **DoR テンプレート未記入検知の強化 (Must 2)**:
   - `templates/template_issue.md` と `template_pre_verification.md` のプレースホルダー記法を堅牢に標準化。
   - `branchDoRGate.js` において、英字プレースホルダー（`<ISSUE_NUMBER>` 等）およびコロン後の空欄項目（`- **現在の問題点**: ` のような未記入行）を確実に検知して拒絶。
   - 「テンプレートそのままをコピーした場合は必ず deny される」テストケースを追加。
3. **safetyGuard の非対話テスト判定の精緻化 (Must 1 & Should 3)**:
   - 設定層で許可されたテストコマンド（または `package.json` のスクリプト）を参照可能にする。
   - npm スクリプト引数の区切り（`-- --run`, `-- --watch=false`）を正しく解釈し、非対話指定を確実に識別。
   - SKILL.md およびガイダンスメッセージの案内と判定を完全一致させる。
4. **プラグインパス・テンプレートパスの動的解決 (Should 5 & 6)**:
   - `import.meta.url` を起点としたプラグインルートの動的解決。
   - Remediation Guidance において、プラグインの絶対パスまたは動的相対パスを正確に案内。
5. **Issue ディレクトリ探索の共通化 (Nits)**:
   - `branchDoRGate.js` と `prePrAuditGate.js` に重複していた Issue ディレクトリ解決ロジックを `hooks/hookUtils.js` に集約。
6. **改行コード正規化 (.gitattributes)**:
   - リポジトリ全体で CRLF/LF の混在を防ぐ `.gitattributes` を追加。
7. **ドキュメント・スキル・エージェントプロンプトの完全汎用化**:
   - `skills/*`, `agents/*` から特定プロジェクトの痕跡、特定ディレクトリ（`src/core/`）、古い ADR 参照を完全排除。

---

## 3. 排除するリスク (Risks to Eliminate)

- **リスク 1: 未記入テンプレートの見切り発車すり抜け**: プレースホルダー検知の穴を突いて不完全な仕様書でブランチ作成されてしまうリスクを物理封じ込め。
- **リスク 2: 正規テスト実行の誤遮断および対話型ハング**: `npm test` が不当に拒絶されたり、フラグ不備で対話型テストが実行されてプロセスが永久ハングするリスクを排除。
- **リスク 3: 特定プロジェクトへの密結合と移植性喪失**: ホストプロジェクト固有のルールを外部設定として注入可能にし、プラグインの汎用性を保証。
- **リスク 4: パス不整合による実行失敗**: 任意のディレクトリ構成やインストール方式（submodule/clone）でパスが壊れるリスクを排除。

---

## 4. 設計方針・アーキテクチャ決定

- **設定分離の原則**: プラグイン内部には妥当なデフォルト値（Convention over Configuration）を持たせ、ホストプロジェクト側で上書き可能とする。
- **多層防御の DoR ゲート**: プレースホルダーのパターンマッチングに加え、必須フィールドの空欄検知を導入。
- **後方互換性の維持**: 既存の 128 件のテストスイートを破壊せず、かつ新しい設定・検証に対応するテストを追加。

## 5. 受け入れ基準 (Acceptance Criteria / Definition of Done)

### 5.1. 機能受け入れシナリオ (Given-When-Then)

- **シナリオ 1: テンプレートそのままコピー時のブランチ作成拒絶**
  - **Given**: `template_issue.md` をそのままコピーして内容を記入していない `issue.md` が配置されている。
  - **When**: エージェントが `git checkout -b feature/issue-5-...` を実行しようとする。
  - **Then**: `branchDoRGate.js` により拒絶（`deny`）され、未記入プレースホルダーまたは空欄項目の是正が指示される。

- **シナリオ 2: 非対話フラグ付き npm test の許可**
  - **Given**: エージェントが `npm test -- --run` や `npm test -- --watch=false` を実行しようとする。
  - **When**: `safetyGuard.js` で検証される。
  - **Then**: `allow` と判定され、安全に実行が許可される。

- **シナリオ 3: フラグなし対話型 npm test の安全な遮断と的確なガイダンス**
  - **Given**: エージェントがフラグなしの `npm test`（または `npm run test`）を実行しようとする。
  - **When**: `safetyGuard.js` で検証される。
  - **Then**: `deny` と判定され、`-- --run` や `-- --watch=false` の付与を促す明確なガイダンスが返る。

- **シナリオ 4: 設定ファイルによるカスタムテストコマンドの許可**
  - **Given**: 設定層で `allowedNonInteractiveCommands` に `["npm test"]` が登録されている。
  - **When**: エージェントが `npm test` を実行しようとする。
  - **Then**: 設定に従って `allow` と判定される。
